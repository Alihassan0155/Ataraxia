# Approved full-catalogue synchronization

Scope: all 4,226 canonical IDs, including the 100 pilot/held-out research videos.
Approval was given on 2026-11-03 after a read-only S3/Supabase audit.

`backend.video_data.full_sync` freezes existing files and validated artifact
entities. It does not invoke models or regenerate embeddings. Genuine contexts
are independent records; an unannotated video can have a real context without
an affect, semantic, or embedding row. Valid Qwen/InternVL history is imported
alongside Gemini, using the existing Reader's identities and validators.

S3 uses the verified `ataraxia` profile and existing bucket. Destinations for new
objects are `videos/{finevideo|tiktok|youtube}/{canonical_id}.mp4`. Eight existing
root-level keys are reused via explicit, content-verified canonical mappings.
Uploads use `IfNoneMatch='*'` and a full-object SHA-256 checksum. HEAD checksum
verification follows each new upload; existing objects use full-download proof
with an unchanged ETag/size, or a fresh streamed hash when necessary. An ETag
alone is never interpreted as a SHA-256 checksum.

The database writer uses only SELECT, INSERT, transaction controls, and locks.
Existing video rows are skipped after storage identity checks; their metadata
is authoritative. Other existing rows must match all projected values exactly.
Each 50-video transaction rechecks primary keys under short table locks. An
unsafe conflict rolls back the batch and isolates individual videos. Failed
operations are checkpointed and remain available for resume. No SQL UPDATE,
DELETE, schema DDL, or placeholder annotation rows are used.

The previous watcher accepts the presence of additional unrelated video IDs
while retaining its original fixed 1,140-video delivery scope. Its configuration
and startup registration remain unchanged. `backend/run_full_sync.py`, run in
the main environment for psutil, stops only that exact watcher process tree,
runs the import-environment synchronizer, and restores its prior running state
in a finally block. The synchronizer also holds the queue OS lock and the same
PostgreSQL advisory lock used by the original writer.

From repository root:

```powershell
.\backend\.venv-import\Scripts\python.exe -B -m backend.video_data.full_sync prepare
.\venv\Scripts\python.exe -B backend\run_full_sync.py
.\backend\.venv-import\Scripts\python.exe -B -m backend.video_data.full_sync verify
```

Re-running the supervisor resumes the frozen plan, rechecks remote state and
skips exact existing rows and objects. Preparation will not replace an existing
plan. New artifacts produced after preparation require a separately prepared
follow-up snapshot; existing artifacts and history are not removed.

Evidence under `backend/reports/full_sync_20261103/`:

- `plan.json`, `media.json`, and table JSONL files: hashed frozen input plan.
- `issues.json`: rejected/deferred source annotations, if any.
- `baseline.json`: original per-row hashes and schema signature.
- `preflight.json`: immediately rechecked planned insert counts.
- `checkpoint.sqlite`, `apply.log`, `execution.json`: resumable execution state.
- `verification.json`, `remaining.json`: relationship/vector validation,
  original-row preservation, coverage, and exact outstanding identities.
- `watcher_state.json`: prior state, restoration and configuration checks.

Validation before execution: 28 targeted unit tests pass, including conditional
creation, checksum verification, conflict rejection, existing metadata retention,
exact vector comparison and transaction rollback. Final production results are
recorded in the verification report, not inferred from these unit tests.
